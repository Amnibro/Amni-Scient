Amni OS 0.5.0

2026-09-25

The biggest release yet. It was measured against 14 leading distros, and most of the gaps found are closed here.

  • Secure Boot works from the USB stick. The live USB boots with Secure Boot on. You enroll the Amni key once in MokManager (ENROLL_THIS_KEY_IN_MOKMANAGER.cer, SHA-1 A1:8C:DD:28:AF:EB:DA:DD:D8:31:FA:97:BE:31:DC:1D:E1:E9:80:0B). Installed systems boot with Secure Boot on as well: GRUB is rebuilt with SBAT and embedded modules. Steps are in docs/signing.md.
  • Encrypted installs boot. LUKS installs now get sd-encrypt and the keyfile in the initramfs. Before this they never booted.
  • Restore points are real. Snapper was never configured on Calamares installs; it is now. snap-pac takes a pair around every update, and every snapshot boots from GRUB on a RAM overlay (systemd.volatile=overlay).
  • Hardware-aware drivers. amni-driver-apply detects this machine's hardware and installs what it needs, including when you plug a device in or pair it.
  • Amni Welcome. A first-login tour covering restore points, drivers, encrypted backups, privacy, your Amni apps and language.
  • Security Center in Control:
    • Installs ask for your password for sudo and admin actions again.
    • AppArmor is on for new installs.
    • Status is shown for encryption, Secure Boot, firewall, updates, restore points and signing.
    • TPM2 disk unlock with a recovery key.
    • Opt-in local crash reports and security advisories.
    • Machines that were passwordless keep that until you switch it in Control.
  • Package and ISO signing. The new amnios-keyring delivers the package key (phase 1), and ISOs are signed with minisign.
  • Languages: Fcitx 5 input methods (Chinese, Japanese, Korean, Vietnamese and more) on Wayland, 23 locales in the live session, and a new High Contrast look.
  • Privacy: the installer no longer looks up your location online. The time zone starts at New York and you pick yours on the map. docs/privacy.md lists every connection the OS makes, and crash dumps are off by default.
  • Recovery tools:
    • an opt-in stable update channel (the Arch Linux Archive, a few days behind)
    • kernel choice with a guaranteed fallback
    • Repair Amni OS (reinstalls system packages and keeps your files)
    • Reset my desktop settings
    • one-click virtual machines (now with a virtual TPM) and Cockpit
  • For bug reports: amni-bug-info prints a privacy-safe system summary. os-release links to the new docs, support, privacy and issue pages at amni-scient.com/amni-os.
  • Project: CI runs on the Amni build PC, not GitHub Actions, and reports to PRs as amni-local-ci. Also added: issue templates, a Linux publish-repo.sh, and tools/qvm.py for headless Secure Boot VM tests.

Package and ISO signing, phase 1

  • New amnios-keyring package carries the Amni OS package-signing key (ed25519, fingerprint C40EC8B9A32CF20378261E96210B8C24BF3E7D1E) and populates it into pacman's keyring. amni-os-core now depends on it, so every install gets the key with its next update.
  • ISOs are signed with minisign by default.
    • publish.sh signs, verifies its own signature, and publishes amnios-iso.pub. It refuses to publish unsigned unless AMNI_UNSIGNED=1.
    • latest.json gains minisig_url and minisign_pubkey.
  • tools/sign-repo.sh signs every unsigned package in the repo and re-signs the database. It is for phase 2 and has not been run on the published repo.
  • The repo stays unsigned until the key has reached installs. A test showed that signing first breaks updates on every install that lacks the key. docs/signing.md has the plan.

Hardware-aware drivers

  • amni-driver-apply installs the drivers each machine needs, and only those. /usr/share/amni-os/drivers.json matches rules against:
    • PCI and USB IDs, and USB interface class (printers)
    • Bluetooth input devices (controllers)
    • laptop chassis or battery, CPU vendor, hypervisor, and DMI vendor
    • NVIDIA generation (legacy or Turing+) and GPU count
  • Required rules install their packages, enable their services and add users to groups. Optional ones (Razer, Logitech, NVMe tools, OpenCL, Intel NPU) are only listed until Control installs them (polkit-helper drivers-optional).
  • It runs:
    • when a USB device is plugged in or a Bluetooth input device pairs (90-amni-drivers.rules, via SYSTEMD_WANTS)
    • at the end of amni-gpu-apply, which is Control's "GPU drivers" button
    • from amni-driver-apply.timer, 4 min after boot and then daily, to retry anything that failed offline
  • It skips the live session, waits for the pacman lock, and never runs -Sy (no partial upgrades). It writes its result to /var/lib/amni-os/drivers.json and sends a desktop notification naming what it installed. Nothing leaves the machine.
  • Rules cover:
    • graphics: Intel and NVIDIA video decoding, hybrid-GPU switching and prime-run on laptops, and NVK Vulkan for pre-Turing NVIDIA
    • laptops: thermald on Intel laptops, and fingerprint readers
    • wireless and phones: Bluetooth file transfer, iPhone/iPad, and USB modems
    • printing: USB driverless printing plus HP, Brother, Samsung and Epson drivers
    • gaming: Xbox controllers over Bluetooth, and the Xbox Wireless Adapter
    • docks: DisplayLink
    • VMs: QEMU, VirtualBox, VMware and Hyper-V guest tools
    • vendor tools: ASUS laptop controls and GPU modes, and Framework tools
  • Small official drivers now ship on the ISO so offline installs still get them. Their services are enabled only on matching hardware.
  • The AUR drivers (brlaser, splix, epson-escpr, xpadneo, xone, supergfxctl, evdi, displaylink) go in the new iso/releng/packages.repo. build-local-repo.sh builds them into [amnios] and bake.sh keeps them off the ISO.
  • scripts/gpu-apply.sh had fallen behind the packaged copy (no Turing check or nouveau fallback). It's synced back so the overlay can't regress the package.
  • Verified on the test PC:
    • A real run installed bluez-obex in 1.9 s, and snap-pac took restore points #6/#7 around it.
    • udevadm test on the attached Razer mouse sets SYSTEMD_WANTS=amni-driver-apply.service.
    • Rule matching was checked on five simulated machines: Dell XPS Intel+NVIDIA, ASUS ROG, a KVM guest, a desktop with an HP printer, iPhone and Xbox pad, and a GTX 1060 with a DisplayLink dock.

Restore points that actually get taken

  • Snapper was never configured on Calamares installs. system-setup ran snapper create-config /, which refuses to run when /.snapshots already exists. Calamares mounts the @snapshots subvolume there, so the step failed and only logged "snapper config failed". snap-pac, the snapper timers and grub-btrfs were all installed and enabled, but no restore point was ever taken.
  • system-setup now writes /etc/snapper/configs/root from snapper's template when /.snapshots is already a subvolume, and still uses create-config when it isn't. It adds root to SNAPPER_CONFIGS and takes a first "Restore points enabled" snapshot.
  • Retention: 10 update pairs (5 marked important), plus 5 hourly, 7 daily and 2 monthly snapshots. The template default was 50 plus 10 each.
  • Booting a snapshot works on the systemd initramfs.
    • grub-btrfs's grub-btrfs-overlayfs hook is busybox-only and does nothing under systemd.
    • The new amni-snapshot-boot initcpio hook packs systemd-volatile-root and overlay.ko.
    • grub-btrfs adds systemd.volatile=overlay to snapshot entries only, so a snapshot boots read-only with a RAM overlay on top. Normal boots don't carry the parameter, so the service exits immediately.
    • installed-cleanup adds the hook to HOOKS only when the hook file exists. system-setup adds it to existing installs and runs mkinitcpio -P.
  • On btrfs with snapper configured, timeshift-autosnap is set to skip, so updates take one snapshot, not two. Timeshift stays the restore-point path on ext4.
  • Verified on the test PC:
    • The baseline snapshot was taken.
    • A pacman transaction produced a snap-pac pre/post pair.
    • grub-btrfsd rebuilt the menu, and each snapshot offers both kernels with the overlay parameter.
    • Both initramfs images contain systemd-volatile-root and overlay.ko.
  • Not verified yet: an actual boot into a snapshot, and a fresh Calamares install.

Unreleased - Bluetooth pairing sees keyboards and mice again

2026-09-23

  • BLE devices never showed up when pairing. KDE Connect's "Bluetooth (beta)" link provider keeps a discovery session open with SetDiscoveryFilter {Transport: "bredr"}, so the adapter only ran Classic inquiry and never an LE scan. Bluetooth Low Energy keyboards and mice (a Dell KB7120W here) stayed invisible while Classic devices appeared, and toggling Bluetooth did not help because KDE Connect re-armed the scan as soon as the adapter came back.

It does nothing when the provider is already off or KDE Connect is not installed. KDE Connect keeps working over LAN, which is what Amni Share uses.

Unreleased - Double-click to install .deb and app tarballs

2026-09-22

  • amni-package-install (amni-os-core, /usr/local/bin): double-clicking a .deb or an app .tar.gz/.tar.xz/.tar.bz2/.tar.zst rebuilds it as a pacman package (group amni-downloaded) and installs it through pkexec, so it lands in the Start menu, a newer download upgrades in place and pacman -R / Discover removes it. Tested on Google Chrome's .deb and the Antigravity tarball.
    • Dependencies come from the NEEDED libraries of the executables (followed through bundled libs, so dlopen()ed shims like Chrome's Qt ones aren't forced in), plus the .deb's Depends mapped to Arch names. Missing ones are pulled from the repos by pacman.
    • .deb: /bin, /sbin, /lib* merged into /usr, apt cron jobs dropped, setuid bits kept (chrome-sandbox), conffiles become backup=, icons Debian installs from postinst (product_logo_*.png) put into hicolor. Maintainer scripts are not run (the dialog says so).
    • Tarballs: unpacked to /opt/<name>, /usr/bin/<name> launcher, .desktop + icon (from the archive, its own .desktop, or an Electron app.asar). Electron apps get their desktop file named after package.json name so the Wayland app_id matches the taskbar. Programs that link no display library are installed as commands only.
    • Replaces the same app installed another way (a foreign/AUR package owning the files) in one transaction; files a repo package already owns are left to it. Archives with no app inside (source, backups) open in Ark; .pkg.tar.* files go straight to pacman -U.
  • amni-package-install.desktop handles the types; /etc/xdg/mimeapps.list (new, in backup=) and skel mimeapps.list make it the default. amni-os-core now depends on kdialog, fakeroot and binutils (makepkg, readelf). Control's "Downloaded apps" card mentions it.
    • Plain .tar (application/x-tar) routes here too, so an uncompressed Arch package like amni-browse-0.14.2-1-x86_64.pkg.tar installs with pacman -U on double-click instead of opening in Ark. A plain tar that isn't an app or package (a data transfer, a repo bundle) is still handed to Ark.
    • .rpm: the header is read for name, version, summary and URL, the payload is unpacked with bsdtar, and it goes through the same /usr merge, icon fix-up and library-dependency scan as a .deb (setuid bits kept; RPM scriptlets are not run and the dialog says so). Tested on Fedora's xeyes: installs, runs, pacman -R removes it.
    • AppImage (type 2): installed as one file in /opt/<name>/ with a /usr/bin/<name> launcher (falls back to APPIMAGE_EXTRACT_AND_RUN without FUSE) and the Start menu entry and icon read out of its squashfs with unsquashfs -o <ELF end>; the AppImage is never executed to install it. It never takes over a package it didn't make: Amni-Connect.AppImage becomes amni-connect-appimage, not an "update" of the amni-connect repo package. Type 1 AppImages get told to run directly.
    • .snap: snapd isn't used, so it says so and offers to search Discover (Flathub) for the app.
    • Packages with no Start menu entry now say which command to run instead of "It goes in your Start menu".
  • amni-windows-run (/usr/local/bin) behind wine-exe.desktop: .exe (including the application/x-msdownload type), .msi (msiexec /i), .bat and .lnk run under Wine; the first run shows a "setting up Windows support" notice while the prefix is created instead of appearing to do nothing. Installers' shortcuts land in the Start menu through Wine's menu builder.
  • Flatpak bundles and refs already open in Discover, which installs them.

v0.4.6.6 - A USB that installs on real hardware

2026-09-22

  • Black screen or frozen splash after the Amni OS logo (any GPU). A drop-in on sddm.service (from 0.4.6.3) started X while plymouth still owned the console, slept 30 seconds, then quit plymouth with --retain-splash. Where X lost that race the splash froze on screen, or the screen went black with no text console behind it (a Radeon desktop hit both). The drop-in is gone; the login screen waits for plymouth to quit, the stock order.
  • Sound on installed systems. pipewire, wireplumber and xdg-user-dirs enable their per-user units with systemctl --global enable in their package scripts, which pacstrap ran before systemd was in the image, so the image shipped without pipewire.socket and wireplumber.service. PipeWire had no session manager, so no devices, and apps using the PulseAudio API hung or crashed on launch (Golf With Your Friends). The bake links them into the image, installed-cleanup enables them on installs, and the amni-os-core install script enables them on every upgrade, which repairs machines installed from older images.
  • Start menu opened on "No matches". syncHomePage() ran once before the stack had its initial page, so the home page went into the stack twice; after any search, going back home failed ("replace: nothing to push") and the menu reopened on the empty search view.
  • Amni-Browse 0.14.2 passes Cloudflare checks. On Linux it claimed to be Chrome 153 and faked navigator.userAgentData on a WebKitGTK engine; Turnstile saw the mismatch, reset the checkbox after every click and blocked some sites. It now sends WebKit's own Safari-style user agent (the fake Chrome data is only added when the user agent claims Chrome). v0.3.2 - the bake, fixed and moved to the NVMe

2026-09-03

The bake had been failing with error: target not found: on every package, including ones as ordinary as curl and base. The cause was a carriage return.

mkarchiso parses the package list with sed '/^[[:blank:]]*#.*/d;s/#.*//;/^[[:blank:]]*$/d', and [[:blank:]] covers space and tab only. A trailing CR survives that and goes into pacman's target list as part of the name. When pacman prints the error the CR returns the cursor, so the log shows a clean name and reads like 239 packages that vanished from the repos. iso/releng/packages.x86_64 had been saved with CRLF, which is why exactly our 239 names failed and none of archiso's 200 did, and why the first error had an empty name - that was the CR-only first line.

  • iso/releng/packages.x86_64 and the rest of the CRLF text files normalised to LF.
  • bootstrap.sh stripped CR from a whitelist of file names and the package list was not on it. It now strips CR from every file that grep -I calls text.
  • bake.sh runs the list through tr -d '\r' and then refuses to start mkarchiso if a CR survives in the staged list.
  • New tools/preflight.sh: CR, malformed names, duplicates, bash -n on every script. A second on Windows against an hour in the VM.
  • -debug packages no longer go into the local repo or onto the image. calamares-debug alone was 179 MB of symbols.

The rig moved from E: to C:. E: is a WD My Passport, a USB spinning disk, and the build root, package cache, squashfs and xorriso were all paying its latency.

  • create-bake-vm.ps1 builds on C:/amni-bake with --nonrotational on --discard on, and copies archlinux.iso across if it is missing.
  • serve.js receives the ISO into C:/amni-bake/incoming.
  • VirtualBox 7 refuses guest connections to the host's loopback unless --nat-localhostreachable1 on. Without it the guest gets an instant RST on 10.0.2.2:8768 and curl reports "Could not connect to server" while the host serves the same URL fine. The create script sets it.
  • The old VM is unregistered, not deleted. E:/amni-bake/Amni Bake.vdi is 102 GB and only about 20 GB of it was ever live, so it can go once a bake off C: is confirmed.
